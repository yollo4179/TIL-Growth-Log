
# 근본적인 문제 : 

1. 근본적인 문제: 웹(HTTP)은 기억 상실증에 걸려 있다.
우리가 인터넷을 할 때 사용하는 `HTTP 프로토콜`은 `**무상태성(Stateless)**` 이라는 특징을 가지고 있습니다.<br>
서버는 `클라이언트`(브라우저)의 `이전 요청`을 전혀 `기억하지 못합니다`<br>
방금 로그인을 했어도, 1초 뒤에 "내 프로필 보여줘"라고 `새로 요청`하면 서버는 `"누구세요?"`라고 되묻습니다.<br>

`이전에 로그인한 바로 그 사람`이다"라는 `상태를 유지(Stateful)`하기 위해 우리는 `쿠키와 세션`이라는 기술을 사용합니다.<br>


# Stateful한 상태 유지하기,  인증(Authentication)과 인가(Authorization)

## 인증 (Authentication - '넌 누구냐?'):
- 사용자의 `신원을 확인하는 과정`입니다.
- "내 아이디는 dev_king이고, 비밀번호는 1234야." -> 서버: "오, DB에 있는 정보랑 일치하네. 너 맞구나!" (로그인)
- 사실 `jwt를 사용`하는 겨우, 쿠키에 `Refresh 토큰`이 있다면, 매번 로그인하지 않아도  서버에서 access 토큰을 얻어와 로그인을 유지할 수 있습니다.

## 인가 (Authorization - '이거 할 권한이 있느냐?'):

- 인증된 사용자가 `특정 리소스`나 `서비스 및 기능`에 접근할 수 있는 권한이 있는지 확인하는 과정입니다.

- 나 방금 로그인한 dev_king인데, 다른 사람 글 좀 지워볼게." -> 서버: "넌 로그인(인증)은 됐지만 일반 유저라서 관리자 권한(인가)이 없어. 접근 금지!"


# 🍪 쿠키 (Cookie)

## `정의:` `브라우저`에 저장되는 아주 작은 텍스트 데이터입니다.

특징 (가장 중요!): 브라우저는 특정 서버(도메인)에 `요청을 보낼 때마다`, 해당 서버에서 예전에 구워준(저장해 둔) `쿠키를 HTTP 요청 헤더`에 알아서(`자동으로`) 딱 붙여서 `보냅니다.`<br>

`단점`: `브라우저에 텍스트 형태로 적나라하게 저장`되므로, 여기에 비밀번호 같은 걸 넣으면 해커들에게 "내 정보 가져가세요" 하는 것과 같습니다.<br>

# 🎫 세션 (Session)
정의: `사용자의 중요한 정보`나 상태를 `서버의 메모리나 데이터베이스`에 안전하게 `저장`하는 방식입니다.<br>

동작 방식: `서버에 진짜 정보를 숨겨`두고, 클라이언트에게는 그 `정보에 접근할 수 있는` key(무의미하고 복잡한 문자열)을 하나 발급해 줍니다. 이것이 바로 `**세션 ID (세션 토큰)**`입니다.<br>

`놀이공원 VIP 팔찌`라고 생각하시면 됩니다.<br>

## 인증 및 인가 과정 ( 프론트와 백엔드에서 일어나는 전체 흐름)
```html

이제 유저가 브라우저를 열고 로그인을 할 때 어떤 일이 벌어지는지 시간 순서대로 엮어보겠습니다.

1. [프론트] 로그인 요청 (인증 시작): 사용자가 ID/PW를 치고 로그인 버튼을 누릅니다.

2. [백엔드] 인증 및 세션 생성: 서버가 DB를 확인해서 정보가 맞으면 로그인을 승인합니다. 그리고 서버의 저장소에 [유저 A의 정보]를 기록하고, 그에 매칭되는 Session ID: sdf8923jkfds를 생성합니다.

3. [백엔드 -> 프론트] 쿠키 굽기: 서버는 프론트엔드에 응답을 줄 때, HTTP 응답 헤더의 Set-Cookie라는 항목에 방금 만든 Session ID를 담아서 보냅니다.

4. [브라우저] 쿠키 저장: 브라우저가 이 응답을 받으면, "아, 서버가 쿠키 저장하래!" 하고 자기만의 쿠키 보관함에 Session ID를 저장해 둡니다.

5. [프론트 -> 백엔드] 인가 요청: 유저가 "내 장바구니 보기" 페이지를 클릭합니다. 이때 브라우저가 똑똑하게 아까 저장해둔 Session ID 쿠키를 HTTP 요청에 자동으로 같이 딸려 보냅니다.

6. [백엔드] 인가 확인: 서버는 요청을 받으면 쿠키 안에 있는 Session ID를 봅니다. "어? 이 팔찌 번호(Session ID) 우리 서버에 있나? 아, 아까 로그인한 유저 A의 팔찌네!" 하고 유저를 식별한 뒤, 장바구니 데이터를 프론트엔드로 보내줍니다.


```

## 세션의 문제점  

질문 : 세션은 서비스 사용할때마다 인가과정을거치니까 db를 뒤지지?<br>
AI : 사용자가 클릭을 하거나 페이지를 이동할 때마다 브라우저는 세션 ID(쿠키)를 서버로 보내고, 서버는 "이 세션 ID가 유효한지, 이 유저가 누구인지, 권한은 있는지" 확인하기 위해 저장소를 뒤져야 합니다.<br>

## 무거운 DB(디스크) 대신 `Redis 또는 Memcached`를 사용할 수도 있지만..... 
```html
`메인 DB` (디스크 기반): 회원 정보, 결제 내역 등 절대 날아가면 안 되는 `영구적인 데이터 저장.` (느림)

`Redis` (메모리 기반): 세션 ID처럼 빠르게 읽고 써야 하며, 날아가도 (다시 로그인하면 되니까) `치명적이지 않은 임시 데이터 저장.` (엄청나게 빠름)

조회를 하긴 하지만, `디스크가 아닌 RAM(Redis)을 뒤지기 때문`에 눈 깜짝할 사이에 인가 과정이 처리되는 것입니다.
```

# 아예 안 뒤지면 안 돼?(JWT의 등장)
- 세션: 쿠키에는 '열쇠(Session ID)'만 있고, 진짜 정보는 서버가 가지고 있음. (저장소 조회 필수)

- JWT (토큰 방식): 토큰 자체에 `유저의 정보와 권한`을 `암호화`해서 다 때려 넣음. 서버는 요청이 오면 DB나 Redis를 뒤질 필요 없이 `암호화 알고리즘(CPU 연산)`으로 이 토큰이 `위조되지 않았는지만 검사(디코딩)`하면 끝입니다.

## `짚고 넘어가야할 교정`: <br>
JWT의 앞부분은 `**'암호화'된 것이 아니라 단순한 'Base64Url 인코딩'**`이라는 점입니다.<br>
누구나 디코딩(해독)해서 안의 내용을 제이슨(JSON) 형태로 볼 수 있습니다.<br>
그럼 왜 안전하냐고요? 말씀하신 `'해시(Hash)'`를 이용한 `'서명(Signature)' 검증` 때문입니다.<br>

JWT 토큰을 실제로 보면 `.` (점)을 기준으로 `세 덩어리`로 나뉘어 있습니다
```html

1) 헤더 (Header - xxxxx): 
토큰의 타입(JWT)과 서명을 만들 때 쓸 `alg:해시 알고리즘`(예: HS256, RS256) 정보가 들어있습니다. (Base64Url 인코딩됨)

2) 페이로드 (Payload - yyyyy):
여기가 바로 말씀하신 `특정 유저 식별 정보`가 제이슨(JSON)으로 들어가는 곳입니다.
유저 ID, 권한(역할), 토큰 만료 시간 등이 담깁니다. (Base64Url 인코딩됨)

3) 서명 (Signature - zzzzz): 
여기가 JWT의 심장입니다. 
서버만 알고 있는 **'비밀키(Secret Key)'**를 사용해서, 헤더와 페이로드를 인자로 `지정된 해시 알고리즘으로 돌려` 만든 결과물입니다.


`조작 불가` 
-- 개발자 모드에서 base 64Url로  디코딩하여 권한 및 페이로드 정보를 수정할 수 있지만, 서버의 비밀키를 모르면 
절대!!! 서버에서 `인가하는 과정`에서 해시값의 결과가 `서명의 값과 일치하지 않기 때문에` 절대 서비스에 접근할 수 없습니다. 
```
JWT를 이용해 인증 및 인가 과정이 서버에서 실제로 돌아가는 순서 (동작 원리)
```html

1. Base64 디코딩 및 제이슨 변환 (유저 식별):
서버는 토큰을 받으면 중간 부분(Payload)을 Base64로 슥 디코딩해서 JSON으로 엽니다.

* "오, 열어보니까 user_id: 123, role: admin 이라고 적혀 있네?" (유저 식별 완료)


2. 해시를 통한 서명 검증 (위조 확인 - 이 부분이 핵심!):

하지만 서버는 이 정보를 바로 믿지 않습니다. 해커가 페이로드를 조작했을 수도 있거든요. 그래서 서버는 자기가 가진 **'비밀키(Secret Key)'**를 꺼내서, 방금 받은 헤더와 페이로드를 직접 해시 함수에 넣어 돌려봅니다.

- "내가 직접 해시 돌려본 결과값(A)이랑, 토큰 맨 끝에 붙어온 서명값(B)이 똑같네? 중간에 아무도 안 건드렸구나!" (검증 통과)

3. 인가 (Authorization):
검증이 끝났으니 비로소 권한을 부여합니다.

"위조되지 않은 진짜 토큰이고, role이 admin이니까 관리자 페이지 접속을 허락(인가)해 줄게!"
```
## 요약

JWT란, Base64로 인코딩된 토큰을 디코딩하여 JSON으로 유저를 식별하고, 서버의 비밀키를 이용한 해시(서명) 검증을 통해 데이터가 조작되지 않았음을 확인한 뒤 인가 처리를 해주는 방식입니다.<br>



# JWT의 단점 보완, Redis를 이용한 토큰 블랙리스트(탈취된 토큰 처리) 

`jwt를 이용한 인가의 단점`:하지만 jwt만을 사용한다면, 액세스 토큰을 통한 해시값 검증으로 빠른 결과를 얻을 수 는 있지만,`서버는 고객의 인증정보를 저장하지 않고` `해시 작업만으로 고객을 식별`하기 때문에, 토큰에 대한 제어권을 상실합니다.<br>
누군가가 토큰을 (스니핑으로)가로채거나 xss를 심어서 토큰을 탈취하여 서비스에 접근한다면 서버는 이를 막을 방법이 없습니다.<br>
즉, `서버 입장에서는 해커와 진짜 유저를 구분할 방법이 전혀 없습니다.`


# 여러가지 생각해볼 수 있는 해결방안 
```html

1단계: 네트워크 스니핑 원천 차단 (HTTPS 적용)
Wireshark 같은 툴로 패킷을 훔쳐보는 것을 막기 위해 통신 자체를 암호화합니다.

HTTPS 환경에서는 해커가 데이터를 가로채도 암호화된 쓰레기 값만 보이므로 JWT 토큰을 알아낼 수 없습니다. 현업에서 HTTPS는 선택이 아닌 필수입니다.

-----------------------------------------------------------------------------------------------
2단계: "훔쳐가도 금방 썩게 만들자" (Access Token 수명 단축)

피해를 최소화하기 위해 토큰의 유효 기간(만료 시간)을 아주 짧게 잡습니다.
API 요청할 때 쓰는 JWT를 Access Token이라고 부르며, 수명을 15분 ~ 30분 정도로 굉장히 짧게 설정합니다.해커가 운 좋게 훔쳤다 해도 15분 뒤면 휴지조각이 됩니다.
----------------------------------------------------------------------------------------------
3단계: 짧은 수명의 불편함 해결 (Refresh Token 도입)

"15분마다 로그인을 다시 하라고? 유저 다 도망가겠네!"

** 이 문제를 해결하기 위해 로그인 시 토큰을 두 개 발급합니다. **
Access Token (수명 15분): 평소에 API 요청할 때 쓰는 토큰.

Refresh Token (수명 1주~2주): Access Token이 만료되었을 때, "나 아직 로그인된 유저 맞으니까 새 Access Token 줘"라고 서버에 요청할 때만 쓰는 교환권.

핵심: Refresh Token은 통신에 자주 노출되지 않으므로 탈취될 확률이 훨씬 적습니다.
-----------------------------------------------------------------------------------------------
4단계: 보관 장소의 철통 보안 (프론트엔드의 고민)
프론트엔드 개발자가 가장 머리 아픈 곳입니다. 브라우저의 어디에 토큰을 저장해야 해커가 못 훔쳐갈까요?

로컬 스토리지(Local Storage)의 위험성: 자바스크립트로 쉽게 접근이 가능해서, 게시판 같은 곳에 해커가 심어놓은 악성 스크립트(XSS 공격)에 의해 토큰이 털리기 쉽습니다.

해결책 (HttpOnly Cookie): 백엔드에서 토큰을 쿠키로 구워줄 때 `HttpOnly`라는 옵션을 달아줍니다. 이렇게 하면 `자바스크립트로는 절대 이 쿠키에 접근할 수 없습니다.` 브라우저가 통신할 때만 알아서 꺼내 쓰기 때문에 XSS 공격으로부터 안전해집니다.

```
# 최선의 해결 방안 (💡 `아이러니: "결국 다시 DB를 쓰게 되는데요?"`)

1. 해커가 아주 희박한 확률로 수명이 긴 `Refresh Token마저 훔쳐 갔다면?`<br>
해커는 Refresh Token이 만료될 때까지 액세스 토큰을 계속 재발급 받을 수 있습니다.(문제점)<br>

2. 혹은 유저가 `"모든 기기에서 로그아웃" 버튼을 눌렀다면?`<br>
(브라우저가 Refresh Token 및 access Token을 함께 보내도 `Token을 거절할 수 있어야 합니다.`)

이때는 서버가 `"이 Refresh Token은 이제 쓰면 안 돼!"라고 기억해야만 합니다.` 그래서 결국 Refresh Token을 관리하고 블랙리스트(Blacklist)를 운영하기 위해 다시 Redis 같은 DB를 도입하게 됩니다.

최종적인 구조

```html

1. "인가(Authorization)는 일단 해시로!" (평상시: 초고속 모드)
유저가 게시판 글을 읽거나 장바구니를 볼 때(99%의 일반적인 API 요청), 서버는 절대 DB나 Redis를 뒤지지 않습니다.

* 프론트엔드가 수명이 짧은 **Access Token(15분)**을 보냅니다.

* 서버는 오직 CPU만 사용해서 토큰의 서명(해시)만 검증합니다.

* 서명만 맞으면 즉시 통과(인가)시킵니다.

* 결과: DB(디스크) I/O가 전혀 없으므로 세션 방식보다 압도적으로 빠릅니다.

------------------------------------------------------------------------------------------
2. "제어권(Control)을 얻기 위한 Redis의 개입"
DB를 아예 안 쓰면 강제 로그아웃이나 해커 차단을 못 하니, 딱 두 가지 상황에서만 Redis를 확인하여 서버가 제어권을 행사합니다.

* 상황 A: Access Token 수명이 다 끝났을 때 (Refresh Token 검증)

A-1: 15분 뒤, Access Token이 만료되어 API 요청이 거절당합니다.

A-2: 프론트엔드는 "나 아직 로그인 유저야!"라며 Refresh Token을 서버로 보냅니다.

A-3: 이때 서버가 Redis를 뒤집니다. "이 Refresh Token이 우리 Redis에 예쁘게 저장되어 있나?"

A-4: 만약 유저가 다른 기기에서 '모든 기기 로그아웃'을 눌렀다면, 서버는 이미 Redis에서 그 Refresh Token을 지워버렸을 겁니다. 그럼 재발급을 거부하고 제어권을 뺏습니다.

* 상황 B: 치명적인 문제 발생! 즉시 차단이 필요할 때 (Blacklist)

"Access Token 수명이 15분인데, 방금 해커한테 털린 걸 알았어! 15분도 기다릴 수 없어, 당장 막아!"
이럴 때를 대비해 **블랙리스트(Blacklist)**를 운영합니다.

B-1: 사용자가 로그아웃을 하거나, 해킹이 의심되어 강제 차단을 해야 할 때 해당 Access Token을 Redis의 블랙리스트 창고에 등록해 버립니다. (토큰의 남은 수명인 15분 동안만 저장하고 자동 삭제되게 설정합니다.)

B-2: 원래는 API 요청이 올 때 서명만 검사하고 끝내야 하지만, 보안이 매우 중요한 서비스(금융 등)에서는 요청이 들어올 때마다 서명 검증 후 "이 토큰 혹시 Redis 블랙리스트에 있니?" 하고 한 번 더 물어보게 설계합니다.

B-3: 블랙리스트에 있다면 서명이 맞아도 인가를 거부합니다.


------------------------------------------------------------------------------------------

```

## 추가적인 질문: 서로 다른 호스트에서 `동시 로그인을 허용하지 않는다면` 어떤 구조로 설계해야할까? <br>
```xml
----------------------------------------------------------------------------------------------

(모바일 환경의 특성): 현대 유저는 스마트폰을 들고 지하철을 탑니다. Wi-Fi를 쓰다가 LTE로 바뀌고, 카페에 가면 또 IP가 바뀝니다. 만약 토큰에 IP를 박아두고 검증한다면? 유저가 5G 기지국을 지날 때마다 IP가 달라서 계속 로그아웃되어 버립니다.


*** 토큰에는 변하기 `쉬운 IP 대신 jti` (JWT ID - 토큰 자체의 고유 식별 번호)를 넣거나, 클라이언트가 생성한 고유한 Device ID(기기 번호)를 넣습니다.***
----------------------------------------------------------------------------------------------
2. 동시 로그인은 허용하나요? (정답: 기획(비즈니스 로직)에 따라 다릅니다!)
동일한 유저가 PC에서 로그인하고 폰에서도 로그인할 때, 서버(Redis)는 이를 어떻게 처리할까요? 서비스의 성격에 따라 두 가지 전략으로 나뉩니다.
----------------------------------------------------------------------------------------------
전략 A: 동시 로그인 허용 (넷플릭스, 슬랙, 구글 등 대부분의 서비스)
동작 방식: 유저 1명이 여러 기기를 쓸 수 있습니다.

Redis 구조: `Redis`에 `유저 정보`를 저장할 때 '1대1'이 아니라 ['1대다(List 또는 Hash)']로 저장합니다.

유저 123의 Refresh Tokens = [<PC의 jti: A>, <아이패드의 jti: B>, <폰의 jti: C>]

장점: 내가 폰으로 넷플릭스를 보다가 PC로 접속해도 폰이 로그아웃되지 않습니다.

특정 기기 로그아웃: 카카오톡의 "다른 기기에서 로그아웃" 버튼을 누르면, 서버는 Redis에서 저 리스트 중 특정 jti만 쏙 지워버립니다.
----------------------------------------------------------------------------------------------
전략 B: 동시 로그인 차단 (은행 앱, 보안 메신저, 특정 모바일 게임)
동작 방식: 한 기기에서 로그인하면 다른 기기는 무조건 튕깁니다.

Redis 구조: Redis는 무조건 1개의 유저당 1개의 토큰만 기억합니다.

상황: 폰으로 로그인한 상태(Redis에 폰 토큰 저장됨)에서 PC로 로그인하면, 서버가 새로 발급한 PC 토큰으로 Redis의 값을 `덮어쓰기(Overwrite)` 해버립니다.

결과: 나중에 폰에서 API를 요청하면 "어? Redis에 있는 토큰이랑 네 폰이 보낸 토큰이 다르네?" 하고 폰을 강제로 로그아웃 시켜버립니다.
----------------------------------------------------------------------------------------------
```
